## 슬라이드 06/17 — PDF 추출 한계와 처리 방식 개선

**구분:** 문제 해결  
**제목:** PDF 추출 한계와 처리 방식 개선

| 항목 | PPT 적용 문구 |
|---|---|
| 텍스트 추출 | 일부 PDF는 텍스트 레이어가 없어 일반적인 방법으로 글자가 추출되지 않았음 |
| OCR 적용 | 텍스트 추출이 안 되는 문서는 페이지 이미지에 Windows OCR을 적용 |
| 표 구조 한계 | 텍스트가 추출돼도 병합 셀과 표의 행·열 관계가 제대로 복원되지 않는 경우가 있었음 |
| LLM·원문 검증 | 페이지 텍스트와 이미지를 LLM에 전달해 혜택 정보를 구조화하고 원문과 대조 |

**하단 핵심 메시지**  
PDF 특성에 맞춰 추출 방식을 보완하고, 구조화 결과는 원문과 대조

**실제 기록에 따른 표현 주의**

- 하나카드 ONE PICK STYLE·PLAY는 **일반 텍스트 추출이 성공**했지만, 기본 표 자동 탐지는 0개였음. OCR로 텍스트 문제를 해결했다고 설명하면 부정확함.
- 우리카드 국제브랜드 서비스안내장은 **텍스트 레이어가 없는 PDF**였고, 실제로 Windows OCR로 추출함.
- OCR 결과에는 숫자·브랜드명 오인식이 남았으므로, 모든 추출 문제를 완전히 해결했다고 표현하지 않음.
- LLM은 페이지 텍스트·이미지를 이용해 구조화했지만, 값과 혜택·조건의 연결 정확성은 별도 검증 대상임.

## 슬라이드 12/17 — 두 가지 구현 접근과 발표 범위

**구분:** 구현 접근 및 담당 범위  
**제목:** 두 가지 구현 접근과 발표 범위

**팀 내 구현 접근**

| 구분 | 접근 방식 | 설명 |
|---|---|---|
| 팀원 구현 | 그래프 모델 중심 | 그래프 스키마를 중심으로 Neo4j를 구성하는 접근 |
| 담당 구현 | PostgreSQL 원장 중심 | RDB 모델을 먼저 구축한 후 Neo4j로 변환·적재하는 접근 |

**슬라이드 설명 문구**  
저는 PostgreSQL에 데이터를 먼저 저장하고, 이를 Neo4j 검색용 그래프로 옮기는 방식을 담당했습니다.

AI 코딩 도구로 구현은 빨라졌지만, 실제 코드와 실행 흐름을 확인하는 데도 시간이 필요했습니다.

**하단 핵심 메시지**  
이후에는 제가 담당한 PostgreSQL 원장 중심 구현을 설명하겠습니다.

**발표 범위 및 표현 주의**

- **팀원 구현:** '그래프 스키마 중심 접근'이라는 큰 방향만 소개함. 팀원의 실제 코드·스키마 세부 내용이나 검증 결과를 직접 확인한 것처럼 설명하지 않음.
- **담당 구현:** PostgreSQL 원장 구축 → Neo4j 변환·적재 → 검증·로그 추적을 중심으로 설명함.
- **AI 활용:** AI가 생성한 코드를 모두 완벽히 분석했다고 주장하지 않음. 확인한 주요 데이터 흐름과 검증 사례를 소개함.
- **비교 금지:** 두 방식의 성능, 정확도, 우열을 실제 비교 검증 없이 단정하지 않음.
- **PPT 구성:** 두 접근 방식과 담당 범위, AI 코딩 경험을 화면에서 바로 설명할 수 있는 짧은 문장으로 표시함.

## 슬라이드 13/17 — 데이터 확인과 오류 추적을 위한 설계

**구분:** 구현 및 검증 구조  
**제목:** 데이터 확인과 오류 추적을 위한 설계

### 01. PostgreSQL 원장 설계
PDF 원문·추출 결과·혜택·조건·검증 이력을 관리

### 02. Neo4j 검색 데이터 반영
원장의 혜택·조건·공식 근거를 그래프에 동기화하고 관계·벡터 검색에 활용

### 03. PostgreSQL 질의 로그 저장
사용자 질문과 검색·응답·오류 정보를 `app_log`에 기록

### 04. 오류 원인 추적
로그와 원장·그래프 데이터를 대조해 문제 구간과 원인 확인

**하단 핵심 메시지**  
원장은 PostgreSQL에, 혜택 검색은 Neo4j에서, 실행 로그는 PostgreSQL에서 관리했습니다.

**구현 및 표현 참고**

- PostgreSQL은 원문·추출·검증 데이터의 원장이며, Neo4j는 검색용 데이터 모델임.
- 사용자 질문 검색 경로는 N 모드(Neo4j 단일 검색)로 통합했음. PostgreSQL을 검색 경로와 완전히 분리한 것이 아니라, 질의 로그 저장 용도로 사용함.
- `app_log` 기록 자체가 자동 오류 원인 분석을 보장하는 것은 아님. 로그·소스 코드·Neo4j·원문 근거를 함께 확인하는 분석 과정임.
- 오류 사례는 해결 완료로 단정하지 말고 실제 수정 및 회귀 검증 결과가 확인된 범위에서 설명함.

## 슬라이드 14/17 — PostgreSQL 원장의 데이터·근거 관리 구조

**구분:** 기술 구현 01  
**제목:** PostgreSQL 원장의 데이터·근거 관리 구조

| 구분 | 주요 테이블 | 관리 내용 |
|---|---|---|
| 01. PDF 원문 | `card_doc` → `card_doc_page` → `card_doc_chunk` | 문서·페이지·청크 단위 원문 관리 |
| 02. AI 추출 이력 | `card_ai_run` → `card_ai_call` → `card_extr_stg` | 실행·호출·추출 후보와 검증 상태 관리 |
| 03. 상품·혜택 정보 | 개별: `card_product` → `card_product_item`<br>공통: `card_common` → `card_common_bnft` | 카드별 상품 항목 및 공통 서비스·혜택 관리 |
| 04. 공식 근거 연결 | `card_source_evidence` + `card_evidence_link` | PDF 인용 근거 보존 및 상품정보와의 연결 |

**하단 설계 핵심**  
PDF 원문, AI 추출 이력, 개별·공통 혜택, 공식 근거를 나누어 저장하고 연결했습니다.

**실제 구현 기준 보충**

- 공통 서비스·공통 혜택은 `card_common`과 `card_common_bnft`에서 관리하며, 카드별 공통 혜택 적용 연결은 `card_common_bnft_apply`가 담당함. PPT 본문에는 개별·공통 구조를 함께 표시하고 연결 테이블은 설명에서만 언급함.
- `card_product_item`에는 혜택뿐 아니라 TERMS, ANNUAL_FEE 등 상품 항목도 포함됨. '혜택 전용 테이블'로 설명하지 않음.
- `card_evidence_link`는 원문 자체가 아니라 카드/상품 항목과 `card_source_evidence` 사이의 연결을 관리함.
- `app_log`, `app_log_event_archive`는 질의·실행 로그 테이블로 PostgreSQL에 보존하며, 13페이지에서 설명함.
- 확인된 PostgreSQL 기본 테이블 20개에는 선언된 FK가 없으므로, PPT의 화살표는 데이터 처리·참조 흐름을 요약한 것이며 실제 FK 제약조건이라고 설명하지 않음.
- 추출 또는 근거 연결 중 검토 대기 상태가 존재하므로, 모든 항목의 원문 검증이 완료됐다고 표현하지 않음.

## 슬라이드 15/17 — PostgreSQL 테이블과 Neo4j 라벨 비교

**구분:** 기술 구현 02  
**제목:** PostgreSQL 테이블과 Neo4j 라벨 비교

**원장 데이터와 검색 데이터의 대응 (PPT 적용용)**

| PostgreSQL 테이블 | Neo4j 노드 라벨 |
|---|---|
| `card_product` | `dp_card_product` |
| `card_product_item` | `dp_card_product_item` |
| `card_common_bnft` | `dp_card_common_bnft` |
| `card_doc` | `dp_card_doc` |
| `card_source_evidence` | `dp_card_source_evidence` |

**슬라이드 설명 문구**  
앞에서 본 PostgreSQL 테이블명에 `dp_` 접두어를 붙여 Neo4j 노드 라벨을 구성했습니다.

실행 로그는 Neo4j가 아닌 PostgreSQL의 `app_log`와 `app_log_event_archive`에 저장합니다.

**하단 핵심 메시지**  
PostgreSQL은 데이터 원장과 실행 기록을, Neo4j는 혜택·근거 검색을 담당합니다.

**발표자 참고 (PPT에 생략)**

- 위 표는 실제 매핑의 일부 예시임. Neo4j 노드 라벨의 접두어는 `dp_`이며, 모든 PostgreSQL 테이블이 1:1 노드가 되는 것은 아님.
- 예: `card_evidence_link`는 `dp_supported_by` 관계, `card_product_doc`는 `dp_has_document` 관계로 매핑.
- PostgreSQL의 `app_log`, `app_log_event_archive`는 그래프 적재 대상에서 제외. 로그 저장은 Streamlit의 별도 경로에서 처리.
- PostgreSQL 원장에 선언된 FK가 없더라도 참조 컬럼을 기준으로 관계를 매핑함. '구조가 완전히 동일하다'는 표현은 피함.
- 소스 근거: `src/card_benefit/docs/guide/POSTGRESQL_TO_NEO4J_SCHEMA_MAPPING.md`

## 슬라이드 16/17 — LangGraph 기반 질문 처리 흐름

**구분:** 기술 구현 03  
**제목:** LangGraph 기반 질문 처리 흐름

**실행 흐름 (PPT 적용용)**

`Streamlit 사용자 질문 → interpret → retrieve → answer → finish → Streamlit 결과 표시`

| 단계 | 역할 | 주요 처리 |
|---|---|---|
| 01. `interpret` | 질문 해석 | Neo4j 후보 검색 및 LLM으로 질문 의도·대상 혜택 선택 |
| 02. `retrieve` | 근거 조회 | 정해진 Cypher로 혜택·조건·PDF 원문 근거 수집 |
| 03. `answer` | 답변 생성 | 조회한 혜택·PDF 근거를 바탕으로 LLM 답변 생성 |
| 04. `finish` | 결과 정리 | 답변·오류·실행 경로를 정리해 최종 상태 반환 |

**조건부 분기 (슬라이드 하단에 짧게 표시)**  
대상 혜택이 없거나 오류가 있으면 `interpret → finish`, 조회 근거가 없으면 `retrieve → finish`로 이동

**슬라이드 설명 문구**  
LLM이 사용자 질문을 해석합니다. Neo4j에서 혜택과 PDF 근거를 조회한 뒤, 그 근거를 바탕으로 LLM이 답변을 생성합니다.

**하단 핵심 메시지**  
Neo4j는 혜택·근거를 검색하고, LangGraph는 질문 처리의 순서와 분기를 관리합니다.

**발표 참고 및 정확성 주의**

- LangGraph는 `CardGraphRAG.run(question)`에서 `graph.invoke(initial_state)`로 실행하며, `CardState`가 단계별로 갱신됨.
- `after_interpret`와 `after_retrieve`가 다음 노드를 선택함. 슬라이드의 한 줄 화살표는 정상 경로를 간략화한 것이며 실제로는 조건부 분기가 있음.
- 일반적으로 질문 해석과 답변 생성에서 LLM을 사용함. 질문 임베딩 API 호출은 별도로 발생할 수 있으며, 예외적인 질문은 답변 LLM 호출이 생략될 수 있음.
- **LLM이 Cypher를 생성하는 구조가 아님.** Neo4j 상세 조회에는 프로그램에 정의된 Cypher를 사용함.
- `finish`는 상태를 정리하며, PostgreSQL `app_log` 적재는 Streamlit/실행 로그의 별도 경로임. `finish`가 DB에 직접 저장한다고 설명하지 않음.
- 이 페이지는 **사용자 질문 실행 흐름**을 설명함. PDF 추출과 PostgreSQL→Neo4j 적재는 실행 전 데이터 준비 단계임.
- 코드·가이드의 링크와 줄 번호는 발표 직전 최신 `main` 소스에서 재확인할 것.

**참고 원문**  
`src/card_benefit/docs/guide/LANGGRAPH_CARD_GRAPHRAG_STRUCTURE_GUIDE.md`

## 슬라이드 17/17 — AI와 함께 구현하며 확인한 점

**프로젝트 구현**  
`PostgreSQL 원장 → Neo4j 검색 → LangGraph 질문 처리`

**개발하며 느낀 점**

- AI 코딩 도구를 활용해 구현 속도를 높일 수 있었습니다.
- 하지만 제가 의도하지 않은 코드가 만들어지거나, Python 답변 검증 로직이 복잡해져 동작을 이해하기 어려웠습니다.
- 복잡한 답변 후처리를 단순화하는 방향을 선택했습니다. 이후에도 실제 답변과 근거를 확인해야 합니다.

**마무리 메시지**  
AI가 코드를 작성하더라도, 결국 개발자가 설계와 실행 흐름을 이해하고 결과를 확인해야 한다고 느꼈습니다.

**마지막 인사**  
감사합니다.

**발표자 참고 (PPT에 생략)**

- 후처리 제거가 실제 소스에 모두 반영·검증됐는지는 Codex 최종 결과로 별도 확인. 이 페이지에서는 '단순화하는 방향을 선택'했다고만 설명함.
- 기존 방식과 Prototype의 정답률 차이는 서로 다른 실행 시점의 비교 결과로, 후처리만이 원인이라고 단정하지 않음. 원본 비교 수치는 실제 로그 확인 후 필요할 때만 별도 자료로 사용.
- 앞부분의 고객 안내·상품 비교·품질 개선은 프로젝트의 활용 목표/방향이며, 실제 구현·검증을 마친 기능과 혼동하지 않도록 발표함.
