## 슬라이드 06/16 — PDF 추출 한계와 처리 방식 개선

**구분:** 문제 해결  
**제목:** PDF 추출 한계와 처리 방식 개선

| 항목 | PPT 적용 문구 |
|---|---|
| 텍스트 추출 | 일부 PDF는 텍스트 레이어가 없어 일반적인 방법으로 글자가 추출되지 않았음 |
| OCR 적용 | 텍스트 추출이 안 되는 문서는 페이지 이미지에 Windows OCR을 적용 |
| 표 구조 한계 | 텍스트가 추출돼도 병합 셀과 표의 행·열 관계가 제대로 복원되지 않는 경우가 있었음 |
| LLM·원문 검증 | 페이지 텍스트와 이미지를 LLM에 전달해 혜택 정보를 구조화하고 원문과 대조 |

**하단 핵심 메시지**  
PDF 특성에 맞춰 추출 방식을 보완하고, 구조화 결과는 원문과 대조

**발표 설명 초안**

처음에는 PDF에서 텍스트를 추출하는 방식으로 접근했습니다. 그런데 일부 문서는 텍스트 레이어가 없어 글자가 추출되지 않았고, 텍스트를 읽을 수 있는 PDF도 표의 행과 열이 제대로 유지되지 않는 경우가 있었습니다.

이에 따라 텍스트 추출이 안 되는 문서는 Windows OCR로 보완했습니다. 또 페이지 텍스트와 이미지를 LLM에 함께 전달해 혜택·조건·한도 등을 구조화했습니다. 다만 OCR과 LLM 결과에도 오류가 생길 수 있어 원문 근거 대조와 검증 과정을 두었습니다.

**실제 기록에 따른 표현 주의**

- 하나카드 ONE PICK STYLE·PLAY는 **일반 텍스트 추출이 성공**했지만, 기본 표 자동 탐지는 0개였음. OCR로 텍스트 문제를 해결했다고 설명하면 부정확함.
- 우리카드 국제브랜드 서비스안내장은 **텍스트 레이어가 없는 PDF**였고, 실제로 Windows OCR로 추출함.
- OCR 결과에는 숫자·브랜드명 오인식이 남았으므로, 모든 추출 문제를 완전히 해결했다고 표현하지 않음.
- LLM은 페이지 텍스트·이미지를 이용해 구조화했지만, 값과 혜택·조건의 연결 정확성은 별도 검증 대상임.

## 슬라이드 12/16 — 두 가지 구현 접근과 발표 범위

**구분:** 구현 접근 및 담당 범위  
**제목:** 두 가지 구현 접근과 발표 범위

**팀 내 구현 접근**

| 구분 | 접근 방식 | 설명 |
|---|---|---|
| 팀원 구현 | 그래프 모델 중심 | 그래프 스키마를 중심으로 Neo4j를 구성하는 접근 |
| 담당 구현 | PostgreSQL 원장 중심 | RDB 모델을 먼저 구축한 후 Neo4j로 변환·적재하는 접근 |

**구현 과정에서 느낀 점**  
AI 코딩 도구로 구현 속도는 높였지만, 생성된 코드의 실행 흐름을 이해하고 데이터·오류를 검증하는 데는 별도의 시간이 필요했음

**하단 핵심 메시지**  
이후 기술 설명은 직접 담당한 PostgreSQL 원장 기반 구현과 검증 경험을 중심으로 진행

**발표 스크립트 (추천, 약 1분)**

이번 프로젝트에서는 Neo4j 데이터 구성에 두 가지 방식으로 접근했습니다. 한 팀원은 그래프 스키마를 중심으로 Neo4j를 구성했고, 저는 PostgreSQL에 관계형 데이터 모델을 먼저 구축한 후 Neo4j에 반영하는 방식을 담당했습니다.

개발 과정에서는 AI 코딩 도구를 적극적으로 활용했습니다. 코드 구현 속도는 빨라졌지만, 만들어진 코드의 실행 구조를 이해하고 실제 데이터로 검증하는 데는 생각보다 많은 시간이 필요했습니다.

프로젝트 일정이 짧다 보니 제가 담당한 코드도 모든 부분을 충분히 분석하기는 어려웠습니다. 주로 데이터 흐름과 주요 실행 경로, 실제 발생한 오류를 중심으로 확인했습니다.

다른 팀원의 구현까지 소스 수준으로 분석하기에는 물리적으로 시간이 부족했습니다. 따라서 이번 발표에서는 두 가지 접근 방식이 있었다는 점만 간단히 소개하고, 이후에는 제가 담당한 PostgreSQL 기반 구현과 검증 경험을 중심으로 설명드리겠습니다.

**13페이지 연결 멘트**  
먼저 데이터를 확인하고 오류 원인을 추적할 수 있도록 전체 구조를 어떻게 나누었는지 말씀드리겠습니다.

**발표 범위 및 표현 주의**

- **팀원 구현:** '그래프 스키마 중심 접근'이라는 큰 방향만 소개함. 팀원의 실제 코드·스키마 세부 내용이나 검증 결과를 직접 확인한 것처럼 설명하지 않음.
- **담당 구현:** PostgreSQL 원장 구축 → Neo4j 변환·적재 → 검증·로그 추적을 중심으로 설명함.
- **AI 활용:** AI가 생성한 코드를 모두 완벽히 분석했다고 주장하지 않음. 확인한 주요 데이터 흐름과 검증 사례를 소개함.
- **비교 금지:** 두 방식의 성능, 정확도, 우열을 실제 비교 검증 없이 단정하지 않음.
- **PPT 구성:** 본문에는 두 접근 방식·경험 한 줄·하단 메시지만 배치하고, 상세 설명은 발표 스크립트로 처리함.

데이터 원장과 검색용 그래프, 실행 로그를 구분해 정확성 확인과 오류 분석에 활용

**발표 설명 초안**

이번 프로젝트에서는 검색 기능뿐 아니라 데이터가 잘못되었거나 답변에 오류가 생겼을 때 원인을 확인할 수 있는 구조를 중요하게 생각했습니다.

PostgreSQL에는 PDF 원문과 추출·검증 이력을 원장으로 관리하고, Neo4j에는 검색에 필요한 혜택·조건·근거 관계를 반영했습니다. 사용자가 질문하면 검색은 Neo4j 중심의 N 모드로 처리하고, 요청과 처리 결과·오류는 PostgreSQL의 `app_log`에 남기도록 했습니다.

이렇게 역할을 분리해서 답변 문제가 발생했을 때 실행 로그에서 질문과 오류를 확인하고, 관련 그래프 데이터 및 원문 근거를 대조하며 원인을 분석할 수 있도록 했습니다. 실제로 카드 비교 질문에서 발생한 `tier value = None` 오류를 재현하고 코드의 변환 부분까지 추적한 사례가 있습니다.

**구현 및 표현 참고**

- PostgreSQL은 원문·추출·검증 데이터의 원장이며, Neo4j는 검색용 데이터 모델임.
- 사용자 질문 검색 경로는 N 모드(Neo4j 단일 검색)로 통합했음. PostgreSQL을 검색 경로와 완전히 분리한 것이 아니라, 질의 로그 저장 용도로 사용함.
- `app_log` 기록 자체가 자동 오류 원인 분석을 보장하는 것은 아님. 로그·소스 코드·Neo4j·원문 근거를 함께 확인하는 분석 과정임.
- 오류 사례는 해결 완료로 단정하지 말고 실제 수정 및 회귀 검증 결과가 확인된 범위에서 설명함.

## 슬라이드 14/16 — PostgreSQL 원장의 데이터·근거 관리 구조

**구분:** 기술 구현 01  
**제목:** PostgreSQL 원장의 데이터·근거 관리 구조

| 구분 | 주요 테이블 | 관리 내용 |
|---|---|---|
| 01. PDF 원문 | `card_doc` → `card_doc_page` → `card_doc_chunk` | 문서·페이지·청크 단위 원문 관리 |
| 02. AI 추출 이력 | `card_ai_run` → `card_ai_call` → `card_extr_stg` | 실행·호출·추출 후보와 검증 상태 관리 |
| 03. 상품·혜택 정보 | `card_product` → `card_product_item` | 카드 상품과 혜택·약관 등 상품 항목 관리 |
| 04. 공식 근거 연결 | `card_source_evidence` + `card_evidence_link` | PDF 인용 근거 보존 및 상품정보와의 연결 |

**하단 설계 핵심**  
원문·AI 추출 이력·상품정보·공식 근거를 구분해 저장하고 추적

**발표 설명 초안**

PostgreSQL은 단순히 카드 혜택만 저장하는 데이터베이스가 아니라, 원본 PDF에서 어떤 정보가 추출됐고 최종 상품정보와 어떻게 연결됐는지 확인하기 위한 원장입니다.

먼저 PDF 문서와 페이지·청크를 보존하고, AI의 실행과 호출, 추출 후보 및 검증 상태를 별도로 기록했습니다. 카드 상품은 `card_product`, 혜택·약관 등 상품 항목은 `card_product_item`에서 관리합니다. 상품 항목의 규칙과 조건은 별도 규칙 테이블로 일괄 분리한 구조가 아니라 `rule_list`, `item_cond_expr` 등 JSON 필드에도 보존됩니다.

또한 PDF에서 인용한 실제 문구는 `card_source_evidence`에, 이를 카드나 상품 항목에 연결하는 정보는 `card_evidence_link`에 관리합니다. 그래서 값뿐 아니라 출처와 추출 과정을 다시 확인할 수 있도록 구성했습니다.

**실제 구현 기준 보충**

- 공통 서비스·공통 혜택 원장은 `card_common`과 `card_common_bnft`에 별도로 관리함. PPT 본문은 공간을 고려해 카드 상품 중심으로 표시함.
- `card_product_item`에는 혜택뿐 아니라 TERMS, ANNUAL_FEE 등 상품 항목도 포함됨. '혜택 전용 테이블'로 설명하지 않음.
- `card_evidence_link`는 원문 자체가 아니라 카드/상품 항목과 `card_source_evidence` 사이의 연결을 관리함.
- `app_log`, `app_log_event_archive`는 질의·실행 로그 테이블로 PostgreSQL에 보존하며, 13페이지에서 설명함.
- 확인된 PostgreSQL 기본 테이블 20개에는 선언된 FK가 없으므로, PPT의 화살표는 데이터 처리·참조 흐름을 요약한 것이며 실제 FK 제약조건이라고 설명하지 않음.
- 추출 또는 근거 연결 중 검토 대기 상태가 존재하므로, 모든 항목의 원문 검증이 완료됐다고 표현하지 않음.

## 슬라이드 15/16 — PostgreSQL 원장 기반 Neo4j 그래프 구성

**구분:** 기술 구현 02  
**제목:** PostgreSQL 원장 기반 Neo4j 그래프 구성

**변환 흐름**  
`PostgreSQL 원장 → 테이블·키·참조 관계 매핑 → Neo4j 노드·관계 적재 → 원장 대조 검증`

| 항목 | PPT 적용 문구 |
|---|---|
| 원장 구조 확인 | PostgreSQL 테이블·PK·참조 컬럼을 기준으로 변환 구조 정의 |
| 노드·관계 구성 | 상품·혜택·문서 등을 노드로, 연결 테이블과 참조 관계를 그래프 관계로 변환 |
| 원본 정보 보존 | 원본 키·행 정보·혜택 규칙 JSON을 보존하고 기존 임베딩 재사용 |
| 적재 후 검증 | PostgreSQL 원장과 Neo4j의 노드·관계·속성을 대조 |

**하단 핵심 메시지**  
독립적인 업무 그래프 모델을 새로 설계하기보다, 기존 PostgreSQL 원장을 검색용 그래프로 변환

**발표 설명 초안**

이번 프로젝트는 처음부터 Neo4j 전용 그래프 모델을 따로 설계한 방식은 아닙니다. PostgreSQL에 문서, 카드 상품, 혜택, 원문 근거를 관리하는 원장을 먼저 구축했습니다.

그 원장의 테이블과 키, 실제 참조 컬럼을 기준으로 Neo4j 노드와 관계를 만들었습니다. 특히 상품 혜택의 규칙과 조건은 별도 그래프 노드로 모두 쪼개지 않고, PostgreSQL의 JSON 데이터를 원본 그대로 보존했습니다. 검색에는 원장에 저장된 임베딩도 재사용했습니다.

이 변환·적재 과정에는 LLM을 사용하지 않았습니다. Python 매핑 코드와 Cypher 적재 로직으로 처리하고, 적재 후에는 PostgreSQL과 Neo4j의 데이터가 일치하는지 검증했습니다.

**용어·구현 기준 참고**

- **PDF 추출과 구분:** PDF의 혜택·조건 구조화 단계에서는 LLM과 Pydantic `PageExtraction`을 사용했지만, **PostgreSQL → Neo4j 적재 단계에는 LLM을 사용하지 않았음**.
- **그래프 스키마가 없는 것은 아님:** 노드 라벨·관계 유형·제약조건·인덱스는 존재함. 별도 도메인 그래프 모델을 완전히 재설계하지 않았다는 의미임.
- **FK 주의:** PostgreSQL 원장에는 선언된 FK 제약조건이 없으므로, 연결은 실제 참조 컬럼과 대상 PK를 대조한 명시적 매핑임.
- **규칙 구조:** `card_product_item`의 `rule_list`, `item_cond_expr` 등은 JSON으로 보존했고, RULE·COND 등 별도 파생 노드를 만들지 않았음.
- **2026-11-06 재구축 검증 기록:** Neo4j 4,359노드·8,648관계, 원장 대조에서 누락·초과·속성 차이 0. 발표 시점 최신 상태는 별도 확인 필요.
