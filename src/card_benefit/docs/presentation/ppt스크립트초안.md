이러한 분석 결과는 향후 상품 기획이나 기존 상품의 개선 사항을 검토하는 데 참고 자료로 활용할 수 있을 것으로 기대합니다.

### 4페이지. 카드 혜택정보의 복잡성

**제목**

하나의 카드 혜택에도 여러 적용 조건이 연결되어 있습니다

**화면 핵심 문구**

ONE PICK STYLE — 대중교통 5% 캐시백

- 전월실적 10만 원 이상
- 월 캐시백 한도 1,000원
- 시외·고속버스 및 철도 등 혜택 제외
- 상품권·공과금 등 실적 산정 제외
- 신규 사용 등록 시 실적 조건 예외

**발표 스크립트**

하나카드 ONE PICK STYLE의 대중교통 혜택을 사례로 살펴보겠습니다.

상품설명서에는 대중교통 5% 캐시백이라는 혜택과 함께 전월실적, 월 한도, 제외 대상, 신규 등록 예외 등의 조건이 명시되어 있습니다.

각 조건은 적용 대상과 범위가 서로 다릅니다.

따라서 고객에게 혜택을 안내하거나 다른 카드와 비교할 때 할인율뿐 아니라 관련 조건을 함께 확인하는 것이 필요합니다.

저희는 이러한 혜택과 조건의 관계를 데이터로 표현하는 데 중점을 두었습니다.

### 5페이지. 상품설명서 데이터의 구조화 과제

**제목**

상품설명서의 혜택과 조건을 비교 가능한 형태로 정리할 필요가 있습니다

**화면 핵심 문구**

- PDF 문서별로 서로 다른 정보 표현 방식
- 표 추출 과정에서 조건 간 관계 손실 가능성
- 동일한 용어라도 카드별 적용 범위에 차이
- 원문 근거를 유지한 데이터 구조화 필요

**발표 스크립트**

카드 상품설명서는 대부분 PDF 형태로 제공되며, 상품마다 혜택과 조건을 설명하는 방식에 차이가 있습니다.

저희 팀이 PDF 추출을 검증하는 과정에서도 일부 표의 열이 누락되거나 여러 할인율이 하나의 항목으로 합쳐지는 사례를 확인했습니다.

또한 상품권 제외라는 동일한 표현도 실적 산정에서 제외되는 경우와 특정 혜택 적용에서 제외되는 경우가 있습니다.

이처럼 상품정보를 정확히 활용하기 위해서는 문장을 추출하는 것뿐 아니라 각 조건의 적용 범위를 구분하고 원문과 연결해 관리하는 과정이 필요합니다.

### 6페이지. GraphRAG 기반 데이터 구성

**제목**

혜택과 조건의 관계를 공식 근거와 함께 관리하는 구조를 설계했습니다

**화면 핵심 문구**

공식 상품설명서

→ PDF 파싱 및 청크 분리

→ 혜택·조건 추출

→ 원문 대조 및 검증

→ PostgreSQL에서 구축·검증·관리

→ 검증 데이터를 Neo4j로 동기화

→ Neo4j 기반 GraphRAG 검색

**역할 분리**

- PostgreSQL: 데이터 원장, 검색 텍스트·임베딩 관리
- Neo4j: 키워드·벡터 검색, 혜택·조건 관계 탐색, 원문 근거 연결

**발표 스크립트**

데이터 구축과 검색은 역할을 나눴습니다. PostgreSQL에서 상품설명서의 혜택·조건을 추출하고 검증하며, PDF 근거와 검색 텍스트·임베딩까지 관리합니다. 검증 데이터는 Neo4j로 동기화해 키워드·벡터 검색과 혜택 관계 탐색, 원문 근거 조회에 활용합니다. 검색 때 전체 데이터를 Python으로 가져오지 않고 Neo4j 내부 Cypher에서 후보와 순위를 계산합니다. PostgreSQL은 정확한 데이터를 관리하고 Neo4j는 연결해 검색합니다. 사용자 질문을 Neo4j에서 처리하는 단일 검색 구조는 최종 목표로, 현재 구현과 검증을 진행 중입니다.

### 7페이지. 활용 방안 ① 정확한 고객 안내

**제목**

공식 근거를 바탕으로 카드 혜택과 이용 조건을 안내합니다

**화면 핵심 문구**

**질문 예시**

ONE PICK STYLE 대중교통 캐시백 조건

**목표 응답 정보**

- 대중교통 5% 캐시백
- 전월실적 10만 원 이상
- 월 한도 1,000원
- 제외 대상 및 예외 조건
- 상품설명서 근거

**발표 스크립트**

첫 번째 활용 방안은 고객을 위한 상품정보 안내입니다.

고객이 특정 카드의 혜택을 조회하면 해당 혜택과 연결된 실적 조건, 한도, 제외 대상, 예외 사항을 함께 제공하는 방식입니다.

여기에 공식 상품설명서의 근거를 연결해 안내 내용의 확인 가능성을 높이고자 합니다.

현재는 이러한 응답을 목표로 데이터 구조와 검색 과정을 구성하고 있으며, 실제 구현 결과에 대해서는 별도 검증이 필요합니다.

### 8페이지. 활용 방안 ② 카드 상품 비교·분석

**제목**

카드별 혜택과 이용 조건을 동일한 기준으로 비교할 수 있습니다

**화면 핵심 문구**

**주요 비교 항목**

- 혜택 대상 및 종류
- 할인율·캐시백·적립률
- 전월 이용 실적
- 월별·건별 혜택 한도
- 실적 및 혜택 제외 조건
- 신규 발급 및 예외 조건

**발표 스크립트**

두 번째 활용 방안은 카드 상품의 비교·분석입니다.

카드마다 혜택과 이용 조건이 다르기 때문에 동일한 기준으로 비교할 수 있도록 정보를 구조화하는 것이 중요합니다.

예를 들어 교통 혜택을 제공하는 여러 카드가 있다면 할인율뿐 아니라 전월실적, 월 한도, 제외 조건 등을 함께 비교할 수 있습니다.

또한 저희가 원문을 대조한 하나카드 4종에서는 상품권 구매에 대한 실적 제외 규칙과 혜택 적용 제외 범위에 차이가 있음을 확인했습니다.

이와 같은 관계를 활용하여 우선 자사 상품 간 비교를 검토하고, 향후 분석 대상 문서가 확보되면 타사 상품과의 비교도 고려할 수 있습니다.

### 9페이지. 활용 방안 ③ 상품 품질 개선 지원

**제목**

상품 비교 결과를 개선 항목 검토에 활용할 수 있습니다

**화면 핵심 문구**

**분석을 통해 살펴볼 항목**

- 유사 상품 간 혜택 수준 차이
- 전월실적 및 한도 조건의 차이
- 복잡하거나 중복된 제외 규칙
- 상품설명서의 불명확한 표현
- 상품 간 조건의 일관성

**활용 흐름**

비교·분석 → 차이점 확인 → 개선 후보 도출 → 담당자 검토

**발표 스크립트**

상품 비교·분석 결과는 기존 상품의 개선 사항을 검토하는 데도 활용할 수 있습니다.

예를 들어 유사한 혜택을 제공하는 카드들의 실적 조건이나 한도를 비교하면 각 상품의 특성을 보다 명확하게 파악할 수 있습니다.

또한 상품설명서에 복잡하게 표현된 조건이나 유사 상품 사이의 차이점을 확인하여 고객 안내 문구의 개선 가능성을 검토할 수 있습니다.

다만 분석 결과만으로 상품의 경쟁력이나 품질을 단정하기는 어렵습니다.

시스템은 비교 결과와 관련 근거를 제공하고, 실제 상품 개선 여부는 담당자가 시장 상황과 상품 운영 정책 등을 종합적으로 고려해 결정하는 방식으로 활용할 수 있습니다.

### 10페이지. 활용 방안 ④ 조건 변경 영향 분석

**제목**

조건 변경 시 관련 카드와 혜택의 영향 범위를 확인할 수 있습니다

**화면 핵심 문구**

**분석 예시**

상품권 구매의 전월실적 제외 규칙 변경

→ 관련 카드별 규칙 확인

→ 연결된 실적 조건 조회

→ 영향 가능성이 있는 혜택 식별

→ 담당자 검토 항목 제공

**발표 스크립트**

카드 상품의 혜택이나 이용 조건이 변경되는 경우 관련 항목을 함께 확인해야 할 수 있습니다.

예를 들어 전월실적 제외 규칙이 변경된다면 해당 규칙이 적용되는 혜택을 검토할 필요가 있습니다.

GraphRAG에 활용하는 관계 데이터를 통해 특정 조건과 연결된 카드 및 혜택을 추적하는 기능을 고려했습니다.

이를 통해 담당자가 변경 영향을 검토할 때 참고할 수 있는 정보를 제공하고자 합니다.

이 기능 역시 향후 구현 및 검증 대상이며, 정책 변경을 자동으로 처리하는 기능은 아닙니다.

### 11페이지. 서비스 활용 구조

**제목**

공통 상품정보를 고객 서비스와 내부 분석 업무에 활용하는 방안을 제안합니다

**화면 핵심 문구**

**공통 상품정보 기반**

카드 · 혜택 · 조건 · 제외 규칙 · 공식 근거

**활용 서비스**

- 고객 AI 상담
- 카드 혜택 조회
- 상품 비교·분석
- 변경 영향 검토
- 내부 상담 및 상품 관리 지원

**연동 방식**

GraphRAG 엔진 + 내부 API / MCP

**발표 스크립트**

구조화된 카드 상품정보는 여러 서비스에서 공통으로 활용할 수 있도록 설계하고자 합니다.

고객 서비스에서는 혜택과 조건을 안내하고, 내부 업무에서는 같은 데이터를 활용해 상품별 차이나 조건 변경의 영향을 분석하는 방식입니다.
